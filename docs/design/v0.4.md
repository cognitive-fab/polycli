## One idea behind 1, 2 and 4: the session settings file is the workstream's configuration

polycli already starts every Claude session with its own `--settings` file (`%APPDATA%\polycli\run\<slot>.settings.json`). It carries the hooks, the status line and the workstream's environment variables, and Claude re-reads it on `respawn` and on reopen. Features 1 and 2 add to that file rather than to launch flags:

- **Plugins**: an `enabledPlugins` map.
- **Permissions**: a `permissions` block (allow, ask, deny, default mode, extra folders).
- **MCP servers**: deny rules for the servers a workstream doesn't use.

Launch flags (`--mcp-config`, `--strict-mcp-config`, `--plugin-dir`) are used only where the settings file can't express something, because a flag is easy to lose on a restart while the file is re-read every time.

A change applies to new sessions at once, and to running ones on **Restart**. The settings dialog says so and offers **Restart the workstream's sessions** (each waits until Claude is idle, as Commit and Push already do).

## 1. Plugins and skills per workstream

### What the user sees

⚙ Settings of a workstream gets a **Plugins and skills** tab:

- **Plugins**: every installed plugin with its version, its context cost (the tokens its skills, agents and tools add to every request) and three choices: *As in Claude* (the default: whatever `claude plugin enable/disable` says), *On* or *Off*. A summary on top: "12 plugins on, about 9,400 tokens of context".
- **Skills**: every skill a session of this workstream would load, grouped by where it comes from (your user skills, this project's `.claude/skills`, each plugin), with its description. Your own and the project's skills have four choices: *On* (the default), *Name only* (Claude sees its name, not its description), *Only when I type it* (`/skill-name`) and *Off*. A plugin's skills follow their plugin's switch (the spike found no per-skill setting that reaches them). A user skill can also be copied into the project (**Copy to this project**), so it travels with the repository.
- A note when the settings differ from what a running session has: "Restart the 2 open sessions to apply".

### How it works

- **Inventory**: `claude plugin list --json` gives id, version, scope, enabled, install path and MCP servers. Skills are read from `SKILL.md` front matter in `~/.claude/skills/*`, `<project>/.claude/skills/*` and each plugin's `skills/*`. Context cost comes from `claude plugin details <plugin>`, parsed from its text. Results are cached in memory with a ↻ Refresh, because each call starts `claude` (one to two seconds).
- **Per workstream**: `w.plugins = { "<id>": true | false }` and `w.skills = { "<skill>": "name-only" | "user-invocable-only" | "off" }`. Only overridden entries are stored; *As in Claude* and *On* are no entry.
- **Into the session**: `writeSettings` adds `enabledPlugins: w.plugins` and `skillOverrides: w.skills` to the session's settings file. A `--settings` value overrides the user's own settings for that session only (fact F1).

### Decisions

- **Three states for plugins, not two.** Storing only overrides means a plugin installed later follows the user's own choice instead of being silently off.
- **Skills use Claude Code's own visibility levels** (`skillOverrides`, fact F2) rather than polycli inventing one: *Name only* keeps a skill reachable while cutting its description out of the context.
- **Context cost is the reason this matters**: the summary line puts a number on what a workstream carries into every request.

### Risks

- Parsing `claude plugin details` text: if its format changes, the cost column shows "?" rather than a wrong number.
- A plugin a running session already loaded keeps working until Restart; the dialog says so.

### Tests

- Unit: settings-file writer with and without overrides; skill front-matter parser (name, description, missing front matter).
- Smoke: a session started with a plugin switched off does not list that plugin's skill in `/skills` (read from the pane).

## 2. MCP servers and permission profiles per workstream

### What the user sees

⚙ Settings gets an **MCP and permissions** tab with two parts.

**MCP servers.** Every server a session of this workstream would get: your user servers, the project's `.mcp.json`, plugin servers and claude.ai connectors, each with *On* or *Off* for this workstream. Health ("connected", "needs sign-in") is shown when known.

**Permissions.** A profile and its rules:

- **Profiles** are kept globally (⚙ in the top bar → Permission profiles) and picked per workstream. They are guardrails: deny and ask rules added on top of whatever the project already allows (a deny wins over any allow, fact F4). Four are created to start with (survey of 2026-11-24, below): two copy rules the user had written by hand, and one is new:
  - *Standard*: nothing added; Claude's own settings and the project's rules apply as today.
  - *No publishing* (as polyaxion's rules): never creates, forks or edits a GitHub repository, never changes git remotes, never runs `npm publish`, and the GitHub MCP tools that create repositories or push files are denied. For experiments that must not leave the PC by accident.
  - *Careful* (as polycheck's rules): asks before web fetch and search, `curl`/`wget`, `git push`, package installs and `npm publish`; denies `rm`.
  - *Live systems*: asks before `aws`, `ssh`, `scp`, `gcloud`, `kubectl`, `docker push` and any command naming `prod`; denies AWS delete and terminate commands. For workstreams that reach servers or cloud accounts. This one is new: no project has such rules yet, and it exists because 388 saved allow rules reach servers and cloud accounts with nothing asking first.
- **Rule hygiene**: the MCP and permissions tab also lists the project's own allow rules (from `.claude/settings.local.json`, where "always allow" saves them), flags rules that contain credentials (keys, tokens, passwords typed into a command) and rules that allow a whole tool, and offers to remove them. polycli changes that file only when the user presses **Remove**.

  The survey that shaped these profiles, over the 48 permission files under `code/`: about 3,500 allow rules saved one approval at a time, 388 of them for commands that push, delete, publish or reach a server or cloud account; four rules allowing a whole tool; credentials inside rules in three projects; deny or ask rules in only two projects, polyaxion and polycheck. Permission prompts are already rare (ten in polycli over three weeks), so profiles are not about fewer prompts: they put back the guardrails that years of "always allow" have worn away.
- A profile is lists of allow, ask and deny rules in Claude's own syntax (`Bash(git push:*)`, `WebFetch`, `mcp__slack`), a default mode (as in Claude, manual, auto, accept edits, plan) and extra folders. An *ask* rule still prompts in auto mode (checked in the spike), so a profile's guardrails hold whatever mode a session runs in.
- A workstream can add rules of its own on top of its profile.
- polycli never offers bypass permissions, as today.

### How it works

- **Into the session**: `writeSettings` adds `permissions: { allow, ask, deny, defaultMode, additionalDirectories }`, the profile's rules merged with the workstream's.
- **MCP servers switched off** become an `mcp__<server>` deny rule in the same block, which removes every tool of that server from the session (fact F3, checked in the spike). The server process may still start; its tools cost no context and can't be called. `disabledMcpServers` in a settings file had no effect in the spike, and Claude keeps its own per-folder list in `~/.claude.json`, which polycli never writes.
- **Inventory**: `~/.claude.json` (user and per-project servers), `<project>/.mcp.json`, plugin servers from `claude plugin list --json`, and `claude mcp list` for health and claude.ai connectors (slow: run on demand, cached).

### Decisions

- **The settings file rather than `--strict-mcp-config`**: strict mode replaces every server with a list polycli would have to rebuild, and a session launched before the change would keep its old flags (respawn keeps launch flags, fact F8), so a change could never reach it. The settings file is re-read on Restart.
- **Profiles are global, rules per workstream**: the same "Careful" applies to every client project, and changing it once changes all of them.
- **Deny always wins** in Claude Code, at any level, so a profile can't loosen a deny in the user's own settings. The dialog shows the user's own deny rules read-only, so nothing looks allowed that isn't.

### Risks

- A rule typed wrong does nothing. The editor checks the syntax (tool name, optional `(pattern)`) and lists Claude's tool names to pick from.
- Users may expect a profile to change a running session; the dialog says Restart.

### Tests

- Unit: profile + workstream merge; MCP-off → deny rule names; syntax check of rules.
- Smoke: a session under *Careful* asked to `git push` raises a permission prompt (the needs-you path), and one with a server off doesn't list its tools.

## 4. Context meter and hand-off

### What the user sees

- The session header shows how full the context is: a thin bar and "62% of 200k". It turns amber past 70% and red past 85%, and the session's tab shows a small dot of the same color.
- At red, a line under the header: "Context is almost full. **Compact** · **Hand off to a new session**".
- **Compact** types `/compact` into the session.
- **Hand off** asks the session to write a hand-off note, then starts a new session in the same folder (or worktree) with the same model, effort and role ("‹role› 2"), whose first prompt is to read that note and continue. The old session moves to Closed, its conversation kept. The new session's prompt list starts with a link back to the old one.

### How it works

- The status line already sends polycli its JSON on every refresh, and that JSON carries `context_window.used_percentage` and `context_window_size` (fact F5). The header reads them; until the first answer (when they are null) it shows nothing.
- The same JSON carries the plan's usage windows (`rate_limits.five_hour` and `seven_day`: percentage used and reset time). The top bar shows them as a small gauge with the reset time, at no extra cost: this was #5 on the list, and it comes free with the meter.
- The hand-off note goes to `<project>/.polycli/handoff/<old session>-<time>.md`, written by Claude from this prompt: *"Write a hand-off note for a new session that will continue this work, to <path>: the goal, what is done, decisions and why, what is in progress, next steps, files and commands that matter, and anything you were told to avoid. Then stop."* polycli waits for Stop and for the file, then launches.
- `PreCompact` and `PostCompact` hook events (fact F6) are added to the session's hooks: the header shows "Compacting…" in between, and the meter waits for the next status line.

### Decisions

- **A note written by Claude, not `--resume --fork-session`**: a fork carries the full context into the new session, which is exactly what is full. The note is the summary, readable and editable before the new session starts (the dialog shows it, with **Start** and **Edit first**).
- **Both choices are offered**: `/compact` keeps one session and is quicker; the hand-off gives a clean session and a document.

### Risks

- The note can miss things. The old session stays in Closed and can be reopened.
- If the model's window is unknown, the meter shows tokens without a percentage.

### Tests

- Unit: context from status-line JSON and from a transcript tail; thresholds.
- Smoke: hand-off on a Haiku session in the smoke folder: note written, new session idle with the first prompt registered, old one closed.

## 6. polywatch in the rail, and the code-review light

### What the user sees

- **In the rail**, next to each workstream and each session: a small badge with the number of confirmed polywatch findings that have no outcome yet, red if one is high severity, amber otherwise. Clicking it opens a **Findings** panel: each finding with its file and place, the claim, Opus's evidence, and **Real** / **False alarm** buttons that record the outcome in polywatch.
- **The code-review light** in each session header, beside the git line: a dot and a word.
  - **Green — no review needed**: polywatch has covered what changed.
  - **Orange — review advised**: something polywatch can't or didn't check.
  - **Red — run a review before you push**.
  
  Hovering lists the reasons ("polywatch ran out of budget on 2 turns: 380 lines of `sessions.js` unchecked"; "`hooks.js` changed in 5 turns and 2 sessions: interactions polywatch doesn't see"). Clicking offers **Run /code-review** on just the files behind the reasons, at the suggested level, and **Run and fix** (`--fix`). It types the command into the session, as if typed in the prompt box (fact F7).
- The workstream's dot in the rail takes the worst light of its sessions. **Push** in the git line asks for confirmation when the light is red.

### The idea: review what polywatch can't

polywatch already reviews every turn, so the light never asks for a review because a lot of code changed. A long session that polywatch checked completely stays green. The light asks for a review only for four kinds of reason, each something a per-turn review can't settle on its own:

1. **Gaps in polywatch's coverage**: turns it skipped or only half checked. Examples: the per-turn or daily budget ran out ("remaining claims were not checked"), the reviewer failed, serious claims were left unchecked, Opus answered *uncertain*, or the turn was too large to send.
2. **Interactions across turns**: polywatch sees one turn's diff at a time. The same file or module changed in several turns, or by several sessions (parallel worktrees), with concurrency, state or protocol code involved, is where per-turn review misses things.
3. **Defects still open**: confirmed findings with no outcome, where no later turn touched the file to fix them. A /code-review doesn't close them; an outcome or a fix does.
4. **A fragile area**: where polywatch keeps confirming defects in the recent turns of a project, the same amount of uncovered code counts for more.

### It learns from your reviews

When `/code-review` runs, it works as a background agent of the session and its findings come back into the session's transcript: as a structured findings record (file, line, severity, verdict) when the host supports one, otherwise as the agent's result, a Markdown list of `**file:line — summary**` lines (seen in the spike). polycli reads either form and compares the findings with what polywatch had already found:

- **A review that found nothing new** after an orange light means the light was too cautious for this project: its thresholds rise a step.
- **A review that found defects polywatch missed** means the light should speak earlier: they drop a step, and the reasons behind that light count for more next time.

The thresholds are kept per project and shown in ⚙ → Code review ("this project: reviews found something new 3 times out of 7"), with **Reset**. So the light adapts to each project instead of using one fixed rule.

Learning has limits, so a run of empty reviews can't silence the light:

- **A bounded range**: each threshold moves at most two steps either way from its default (from half to double).
- **Two reasons are never learned away**: an open high-severity finding is always red, and code polywatch left unchecked at push time is always at least orange once it passes the default amount. Learning only changes how much interactions (reason 2) and fragile areas (reason 4) count.
- **Recent reviews weigh more**: only the last ten reviews of a project count, so an old run of quiet reviews fades.

### How it works

- **polywatch's records**: `<main repository>/.polywatch/ledger.jsonl`, read incrementally (only complete lines) and watched for changes. A `review` record names the Claude session (matched by `sessionId`), its tier, files, changed lines, concurrency, state and protocol hits, its notes (budget, errors), the claims raised and how each check ended, and its findings. `finding-outcome` records close findings.
- **The span**: during work, from the session's last `/code-review` (polycli records every prompt). At **Push**, **Publish** or a PR, the whole branch (`merge-base..HEAD`), across every session that worked on it. That is the moment the light is for.
- **Score**: each reason adds points: unchecked changed lines in coverage gaps (doubled for HARD turns); files changed in three or more turns or by two or more sessions with concurrency, state or protocol hits; open findings (a high one alone is enough for red); multiplied by the area's recent defect rate. Orange and red are two thresholds on that score, adjusted per project by the learning above. During work the light stops at orange, except for an open high finding; red is for push time.
- **Where to look**: the reasons carry their files, so the suggested `/code-review` names them (`/code-review high app/src/main/hooks.js app/src/main/sessions.js`) instead of the whole branch.
- **Without polywatch** in a project, every change is a coverage gap, so the light works from git alone (changed lines and files since the last review) and says so.
- **Recording an outcome**: runs polywatch's own command, `polywatch.mjs outcome <review> <n> real|false --by user --dir <root>`, found through `claude plugin list --json` (the polywatch plugin's install path). polycli never writes the ledger itself. `/code-review` findings appear in the Findings panel too, marked as from a review.

### Decisions

- **Not a turn counter**: amount of change alone never lights orange when polywatch checked it all.
- **Reasons, with files, are always shown**: a light without a why is noise, and the files make the review smaller.
- **The light suggests, never blocks**: Push asks once when red, nothing more.
- **It adapts per project** from what reviews actually find, and the user can see and reset what it learned.
- **polywatch owns its data**: outcomes go through its command, so its own dashboard and calibration see them.

### Risks

- A session in a worktree: the ledger lives in the main repository's `.polywatch`; the git root is resolved through `git rev-parse --git-common-dir`.
- Too few reviews to learn from: the per-project adjustment starts after three reviews and moves one step at a time.
- A `/code-review` whose output format changes: findings are read from the structured record or the `file:line` lines of the agent's result; if neither is found, nothing is learned from that run, and the light says "couldn't read the last review".

### Tests

- Unit, over synthetic ledgers and transcripts: each reason alone (budget-cut turn, uncertain check, file changed in 3 turns with state hits, open high finding, fragile area); a long fully checked session stays green; the push span covers several sessions; learning up and down a step, stopping at its bounds, and never silencing an open high finding or unchecked code at push time; open findings survive a /code-review.
- Smoke: append records to a test ledger and see the badge and the light change; Real/False writes an outcome through polywatch.

## 7. Worktree manager

### What the user sees

A **Worktrees** view (next to Docs and Tests) for the workstream's repository:

| Worktree | Branch | State | PR | In use | |
|---|---|---|---|---|---|
| main checkout | master | 1 ahead | | | |
| artifacts-view | worktree-artifacts-view | merged | #12 merged | — | Remove |
| v04-design | worktree-v04-design | 2 ahead, dirty | | Claude session (running) | |
| node-pty-beta | worktree-node-pty-beta | merged | | lock left by an ended session | Remove |

- State: ahead/behind the default branch, uncommitted changes, merged or not.
- In use: a polycli session working there, or Claude Code's own lock ("claude session ‹name› (pid N)"), marked *ended* when that process no longer runs.
- Actions per row: **Open in VS Code**, **Shell here**, **Remove**. On top: **Clean up merged** removes every merged, clean, unused worktree and deletes its branch.

### How it works

- `git worktree list --porcelain` for paths, branches and locks; `git status --porcelain` per worktree; `gh pr list --head <branch> --state all --json number,state,url` when `gh` is available.
- **Merged** means either: the branch's tip is in the default branch (`git merge-base --is-ancestor`), or its pull request was merged on GitHub. The second covers squash and rebase merges, whose commits never reach the default branch as such.
- Remove: `git worktree remove <path>` (adding `git worktree unlock` first when the lock's process has ended), then delete the branch: `git branch -d` when its tip is in the default branch, and `git branch -D` only when GitHub reports its PR merged and the branch has no commits after the PR's last one. Any other branch is kept.

### Decisions

- **Never removes** a worktree with uncommitted changes, one a polycli session works in, or one locked by a running process. Those rows show why the button is missing.
- **A branch is deleted only when its work is merged** (in git, or by its GitHub PR); otherwise it is kept even if the user removes its folder, and the row says "branch kept: not merged".
- Clean up merged shows the list it will remove and asks once.

### Tests

- Unit: porcelain parser (locked with reason, detached HEAD, prunable); lock-is-stale check.
- Integration: a temp repo with three worktrees (merged clean, unmerged, dirty): only the first is removed by Clean up merged.

## 9. Command palette and search everywhere

### What the user sees

- **Ctrl+K** opens a palette over the window. Typing filters, with the best matches first:
  - workstreams, sessions (open and closed), shells, views ("polytwin · Docs"), artifacts and documents;
  - commands: New session, New shell, Restart, Compact, Hand off, Run /code-review, Commit, Push, Open in VS Code, Clean up worktrees, Settings…
- Typing `?` (or Tab to the **Search** tab) searches text across all workstreams: prompts sent to sessions, artifact titles and descriptions, document names, board cards. Each result opens where it lives (the session scrolled to that prompt, the artifact in its viewer).
- A **global hotkey** (Win+Alt+C, as DESIGN.md §9 already set; changeable in ⚙) brings polycli to the front with the palette open, from anywhere in Windows.

### How it works

- Items are built in the renderer from the state it already has; artifacts from the Artifacts list (main process); prompts from `%APPDATA%\polycli\data\prompts\*.jsonl`, searched in the main process (they are small: 200 prompts per session at most).
- Matching: subsequence fuzzy match with boosts for word starts and recent use; results capped at 50.
- The hotkey uses Electron's `globalShortcut`. If another app holds the key, ⚙ says so and offers another.

### Decisions

- **No new index**: the data is small and already on disk; a scan per keystroke (debounced) is fast enough. An index is added only if search passes 100 ms.
- **Commands act on the active workstream or session**, as the toolbar buttons do, and say which in the row ("Restart · polytwin · main").

### Tests

- Unit: fuzzy ranking; prompt search over fixture files.
- UI (CDP, as the Artifacts tests did): Ctrl+K → type → Enter opens the right session; `?pong` finds the smoke prompt.

## 10. Auto-update, and settings export and import

### What the user sees

- **Updates**: an installed polycli checks GitHub Releases at start and every six hours. When a new version is downloaded: a quiet line at the bottom, "polycli 0.4.1 is ready. **Restart to update**", with **What's new** (the CHANGELOG section). Claude sessions keep running through the restart, since they are background sessions, but shells end: a command running in one (a dev server, a deploy) stops, and pinned shells start their command again afterwards. So the line names the shells that are busy ("2 shells are running a command"), and the update can wait: **Restart now**, or **Update when I quit**. ⚙ has **Check for updates** and a switch to turn checks off. Runs from source never update themselves.
- **Export**: ⚙ → **Export settings…** saves a `.polycli.json` file: workstreams (name, color, folder, deploy command, billable), the names of their environment variables (never the values), plugin and MCP choices, permission profiles, pinned shells, code-review thresholds, app settings.
- **Import**: ⚙ → **Import settings…** shows what the file holds and what will be added or replaced, asks for a new folder when one doesn't exist on this PC, and asks for the values of the environment variables it names.

### How it works

- `electron-updater` with the GitHub provider (`cognitive-fab/polycli`). `npm run release` builds, checks and publishes the installer, the zip and `latest.yml` to a GitHub release (draft first; publishing it is the user's step). A GitHub Actions workflow on `windows-latest` runs the same on a tag, so a release doesn't depend on one PC.
- The installer's own `installer.nsh` already closes the installed polycli and waits for its processes; an update runs it silently.
- Export and import are plain JSON with a version field; import validates every field as the app's own dialogs do.

### Decisions

- **Unsigned for now**: updates still work (electron-updater checks the file's hash from `latest.yml`), and SmartScreen warns only on the first manual install. Signing can be added without changing this design.
- **The user publishes**: a release is created as a draft; nothing reaches other people until the user publishes it on GitHub.
- **Values never leave the PC**: variable values are encrypted with Windows' own key for this user and can't be moved anyway.

### Tests

- Unit: export → import round trip; import of a file with a missing folder and unknown fields.
- Release dry run: build with a fake feed (`dev-app-update.yml` pointing at a local folder) and see the update offered and applied in an installed test copy.

## Design review

Things that cut across the features, and what changed in review:

- **One settings dialog, four tabs.** ⚙ Settings of a workstream becomes tabs: *General* (name, color, folder, deploy, billable), *Environment* (today's variables and keys), *Plugins and skills* (1), *MCP and permissions* (2). Every tab saves into the same workstream record and shows the same "Restart N sessions to apply" line.
- **One reader of each source.** The polywatch ledger (6), the status line (4) and `git` (6, 7) each have one reader in the main process that the features share, so a session isn't asked the same thing twice.
- **The viewbar fills up.** Main, Board, Architecture, Docs, Tests, Artifacts, and now Worktrees: seven. At narrow widths the bar becomes a menu after the fourth view. The palette (9) also opens any view by name.
- **Restart is the one way changes reach a running session** (1, 2). The dialog offers **Restart the workstream's sessions**, which waits for each to be idle, so nothing is cut off mid-answer.
- **Nothing polycli adds is hidden from Claude Code's own tools.** Plugins, skills, MCP servers and permissions are written as ordinary Claude settings in the session's settings file: `/permissions`, `/mcp` and `/skills` inside a session show exactly what polycli set.
- **Leftover from 0.3**: polywatch confirmed three defects in the Artifacts view (Markdown images beside the file don't load; a transcript line being written can be missed; overlapping list loads can show stale results). They are fixed first, in phase 1.

### Decisions

Settled on 2026-11-24:

1. **Worktrees** get a view of their own.
2. **The code-review light** works as redesigned: coverage gaps, cross-turn interactions, open defects and fragile areas, learning per project within bounds.
3. **Releases** are built by a GitHub Actions workflow, at no cost: Actions on GitHub's standard runners (Windows included) and release files are free for a public repository on the Free plan. The workflow uses only `windows-latest` and the repository's own `GITHUB_TOKEN` (no paid runners, no extra secrets). If the repository ever becomes private, Windows minutes would count against the Free plan's monthly allowance at twice the Linux rate, and the workflow would have to be reconsidered.

Still open:

4. **Starting permission profiles**: revised after a survey of the existing rules to *Standard*, *No publishing*, *Careful* and *Live systems* (section 2), two copied from rules already in use and *Live systems* new. Confirmed on 2026-11-24; profiles are editable in the app either way.

### How each phase is checked

- The unit tests named in each feature's *Tests*, added to `npm test`.
- `npm run smoke` (the full Claude flow) after every phase, since every phase touches session start-up or the window.
- A new smoke mode per feature where the design names one (`smoke.js settings`, `handoff`, `polywatch`, `palette`), runnable on its own.
- Phase 8 and 9: `npm run dist` and its check, an install over 0.3.0, and one update from a local feed.
- polywatch reviews each phase as usual; its confirmed findings are fixed before the merge.
